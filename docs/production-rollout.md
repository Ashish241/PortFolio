# Production rollout proposal (approval required)

This proposal covers the existing `Ashish241/PortFolio` repository, Vercel project `port-folio`, Render service `ashish-spidey-api-dqj3`, and persistent Neon PostgreSQL database. It has not been applied. The current production URL stays `https://port-folio-delta-wine.vercel.app/`.

## Verified current state

- Vercel is connected to `Ashish241/PortFolio`. `main` produces the production deployment and `new-spiderman-portfolio` produces a preview. `VITE_API_BASE_URL` is set to `https://ashish-spidey-api-dqj3.onrender.com/` for Production and Preview. The repository-root `vercel.json` declares Vite and builds `frontend`.
- Render is Blueprint-managed, connected to the same GitHub repository, and currently builds `new-spiderman-portfolio`. Its Dockerfile path is `./backend/Dockerfile`, context is `.`, auto-deploy is Off, and health check is `/api/ready`.
- GitHub runs `frontend`, `backend`, and `container` jobs for pushes to `main` and `new-spiderman-portfolio` and for pull requests. The active `Main Branch Protection` ruleset currently targets **zero branches**, so its pull-request requirement does not protect `main`; status checks are not required.
- The backend Docker command runs Alembic migration then idempotent portfolio seed exactly once on service startup. There is no separate CI migration against Neon. Contact messages and delivery statuses are outside the portfolio seed.

## Exact changes to approve and apply in order

1. **GitHub ruleset:** Edit the existing `Main Branch Protection` ruleset to target the branch name `main`. Keep deletion and force-push restrictions and pull-request requirement. Enable required status checks `frontend`, `backend`, and `container` from the `Portfolio checks` workflow; require the branch to be up to date before merge. Review the existing signed-commit requirement before activating it because it may block merges made by the current account. No direct production push or merge during setup.
2. **Vercel:** Keep the existing Git integration, production branch `main`, project, and production domain. Do not create a deploy hook or second deployment workflow. Confirm the effective build uses repository-root `vercel.json` (`framework: vite`, `cd frontend && npm ci`, `cd frontend && npm run build`, output `frontend/dist`). Project-level Framework Preset currently displays Next.js, despite the repository override and working production deployment; set it to Vite only if the next preview's effective build does not use `vercel.json`. Retain the existing `VITE_API_BASE_URL` value for Production and Preview.
3. **Render:** In the existing service's Blueprint, change only `branch: new-spiderman-portfolio` to `branch: main` and `autoDeploy: false` to `autoDeployTrigger: checksPass`; sync the Blueprint once after the protected GitHub branch and feature preview checks pass. Do not enable Render On Commit or add a deploy hook. Keep all existing environment variable names and secret values, Dockerfile/context, service URL, and `/api/ready` health check.
4. **Neon:** No database recreation or second migration runner. Keep the current startup path `alembic upgrade head && python -m app.seed && uvicorn ...`. The new education records are content-only seed updates; there is no schema migration. Verify existing contact-message count and delivery statuses before and after the first approved backend deploy.
5. **Release:** Merge the reviewed feature PR to `main` only after the above configuration is approved and all three CI jobs are green. Vercel's Git integration deploys the frontend once. Render's native `checksPass` trigger deploys the backend once. Confirm Render deploy status plus `GET /api/health`, `GET /api/ready`, and the existing Vercel production URL. On failure, stop further merges, inspect the failing provider's logs, and use its rollback to the prior deployment; do not reset Neon or replay failed emails.

The order matters: the currently inactive GitHub ruleset must protect `main` before automatic production delivery is enabled. The actual Render Blueprint edit and hosting-setting changes require the owner's approval first.
